# backcheck

Чекер лабораторных работ курса «Backend-разработка». Он отправляет запросы к запущенному сервису и по каждому пункту чек-листа лабы печатает ✓ или ✗. Язык и фреймворк бэкенда значения не имеют: проверяется только то, как сервис отвечает по HTTP.

## Установка

Нужен Python 3.10 или новее.

```bash
pipx install git+https://github.com/bozhedom/backcheck@v1

# если pipx нет:
pip install --user git+https://github.com/bozhedom/backcheck@v1

backcheck --version
```

Обновление до свежей версии: `pipx reinstall backcheck` или `pip install --user --force-reinstall git+https://github.com/bozhedom/backcheck@v1`.

На Windows после `pip install --user` команда `backcheck` может не находиться. Тогда работает запуск через модуль: `python -m backcheck --lab 1`.

## Запуск

Чекер запускается из корня своего репозитория, там, где лежит `contract.json`. Сервис в этот момент должен быть запущен.

```bash
backcheck --lab 1                   # база лабы 1, шесть пунктов
backcheck --lab 1 --stars           # база и звёздочки
backcheck --lab 2 --only 6          # только пункт 6
backcheck --lab 3 --all             # базы лаб 1, 2 и 3 подряд, чтобы проверить, что старое не сломалось
backcheck --lab 4 -i                # интерактивный режим: на ручных пунктах спрашивает [y/n]
backcheck --lab 1 -v                # печатать каждый запрос и ответ, удобно для отладки
backcheck --lab 3 --stars --report  # записать backcheck-report.md для описания PR
```

| Флаг | Что делает |
| --- | --- |
| `--lab N` | Номер лабы, от 1 до 5 |
| `--stars` | Проверить ещё ★ и ★★ |
| `--all` | Базы всех лаб от 1 до N |
| `--only K` | Только пункт K базы |
| `-i` | Интерактивный режим: ручные пункты превращаются в вопросы `[y/n]`, пункты с действием ждут Enter |
| `--url URL` | Адрес сервиса вместо `base_url` из `contract.json` |
| `--contract PATH` | Путь к `contract.json`, если он лежит не в текущей папке |
| `--report` | Записать `backcheck-report.md`: хэш коммита, время, версия чекера, результаты |
| `--keep` | Не удалять записи, которые создал чекер |
| `--ci` | Режим CI для лабы 5: чекер сам делает `cp .env.example .env` и `docker compose up` |
| `-v` | Подробный вывод: `>` запрос, `<` ответ |

Код выхода: `0`, если в базе нет ✗; `1`, если есть хотя бы один ✗; `2`, если сервис не отвечает или `contract.json` заполнен неверно.

Свои тестовые записи и пользователей чекер создаёт с префиксами `bc_` и `backcheck-`, а в конце прогона удаляет созданные записи.

### Ещё две команды

```bash
backcheck jwt <токен>             # разобрать JWT: header, payload, сколько осталось жить
backcheck ask --lab 3 --edit      # случайный вопрос из банка лабы и живая правка
```

## Как читать вывод

| Значок | Что значит |
| --- | --- |
| ✓ | Чекер сам отправил запросы, всё совпало |
| ✗ | Чекер сам отправил запросы, и что-то не так. Рядом написано, что именно |
| `>>` | Действие: чекер просит перезапустить сервис или удалить запись в интерфейсе, ждёт Enter и потом проверяет результат |
| ? | Ручной пункт: то, чего не видно по HTTP (README, хэш пароля в базе, интерфейс). С флагом `-i` превращается в вопрос `[y/n]` |
| ⚠ | Предупреждение. На баллы не влияет, но на приёме про это могут спросить |

Без `-i` ручные пункты помечаются «проверка вручную» и не считаются ни ✓, ни ✗. В итоге видно, сколько пунктов прошло автоматически и сколько ждут ручной проверки.

Пример вывода:

```
━━ Лаба 1. HTTP CRUD в памяти ━━

  2  GET /health
      ✓ GET /health: 200 {"status":"ok"}
      итог: ✓ засчитано

  ...

  6  Плохие запросы: 400, сервер жив
      ✓ битый JSON: 400
      ✓ пустое title: 400
      ✓ без title: 400
      ✓ сервер жив после плохих запросов
      итог: ✓ засчитано

━━ Итог ━━
Лаба 1: база 5/6 + 1 на ручную проверку  ?✓✓✓✓✓  порог «принята» (≥ 4) пройден
```

Здесь пункт 1 ручной: чекер нашёл README и `requests.http`, а понятен ли раздел «как запустить», решает человек. С флагом `-i` этот вопрос задаётся прямо в терминале.

## contract.json

Темы у всех разные, а чекер один. Поэтому в `contract.json` описывается своя тема: как называется ресурс, какие поля у сущности, какие запросы должны давать ошибку. Файл растёт от лабы к лабе. Ниже полный пример для темы «Трекер привычек» после лабы 5.

```json
{
  "base_url": "http://localhost:8000",
  "resource": "habits",
  "id_field": "id",
  "missing_id": "999999",
  "list_key": null,
  "create": { "title": "Пить воду", "goal_per_day": 8, "status": "active" },
  "update": { "title": "Пить много воды" },
  "required_field": "title",
  "errors": [
    { "body": { "title": "" }, "field": "title" },
    { "body": { "goal_per_day": -1 }, "field": "goal_per_day" },
    { "body": { "status": "unknown" }, "field": "status" }
  ],
  "filter": { "param": "status", "value": "active", "other": "archived" },

  "text_field": "title",
  "sort": { "param": "sort", "value": "title", "field": "title" },
  "child": {
    "resource": "checks",
    "create": { "date": "2026-10-01" },
    "parent_field": "habit_id"
  },
  "rule": {
    "description": "Нельзя отметить привычку дважды за один день",
    "setup": [{ "method": "POST", "path": "/api/habits/{id}/checks", "body": { "date": "2026-10-01" } }],
    "violate": { "method": "POST", "path": "/api/habits/{id}/checks", "body": { "date": "2026-10-01" } },
    "expect_status": 409
  },
  "stats_path": "/api/habits/stats",

  "auth": {
    "scheme": "basic",
    "register_path": "/auth/register",
    "login_path": "/auth/login",
    "me_path": "/auth/me",
    "login_field": "username",
    "password_field": "password",
    "token_field": "access_token",
    "owner_field": "owner_id",
    "admin": { "username": "admin", "password": "admin-test-pass" }
  },

  "frontend_url": "http://localhost:5173",

  "compose_service": "backend",
  "public_url": null,
  "second_service": null
}
```

| Поле | Лаба | Зачем |
| --- | --- | --- |
| `base_url` | 1 | Адрес сервиса |
| `api_prefix` | 1 | Префикс путей, по умолчанию `/api` |
| `resource` | 1 | Имя ресурса во множественном числе, путь будет `/api/<resource>` |
| `id_field` | 1 | Как называется id в ответе, по умолчанию `id` |
| `missing_id` | 1 | Заведомо несуществующий id для проверки 404. Если id это UUID, сюда пишется любой несуществующий UUID |
| `list_key` | 1 | `null`, если список приходит массивом; `"items"`, если ответ выглядит как `{"items": [...]}` |
| `create` | 1 | Правильное тело для создания. Все поля должны вернуться в ответе с теми же значениями |
| `update` | 1 | Какие поля поменять при обновлении |
| `required_field` | 1 | Обязательное поле. Чекер отправит его пустым и не отправит вовсе, в обоих случаях ждёт 400 |
| `errors` | 1 ★ | Неправильные тела. Поля из `body` подставляются поверх `create`, ожидается 400 и `{"error": "...", "field": "<field>"}`. Нужен хотя бы один случай на каждое поле из `create` |
| `filter` | 1 ★ | Параметр фильтра, подходящее значение и неподходящее |
| `openapi_path` | 1 ★★ | Путь к OpenAPI JSON, если он нестандартный. `/openapi.json`, `/swagger.json` и `/v3/api-docs` чекер находит сам |
| `text_field` | 2 | Строковое поле, в которое чекер запишет строку с SQL-инъекцией |
| `table` | 2 | Имя таблицы, если оно отличается от `resource` |
| `sort` | 2 ★ | Параметр сортировки и поле, по которому сортируется. Минус в начале значения означает сортировку по убыванию |
| `child` | 2 | Вторая сущность: `resource` (путь будет `/api/<resource>/{id}/<child.resource>`), тело `create` и поле связи `parent_field` |
| `rule` | 2 ★★ | Фишка темы: подготовительные запросы `setup`, запрос, который нарушает правило, `violate`, и ожидаемый код. `{id}` в пути заменяется на id родителя, которого создаст чекер |
| `stats_path` | 2 ★★ | Эндпоинт статистики |
| `auth` | 3 | Пути и имена полей авторизации. `scheme`: `basic` или `bearer`. `register_extra`: дополнительные поля регистрации, например email. `admin`: тестовый админ из сидов, нужен для ★★ |
| `frontend_url` | 4 | Адрес фронтенда, нужен для проверки страницы и CORS |
| `compose_service` | 5 | Имя сервиса бэкенда в compose, нужно для логов и перезапуска |
| `public_url` | 5 ★★а | Публичный адрес деплоя |
| `second_service` | 5 ★★б | Второй сервис: `name` в compose, `trigger` (запрос к основному сервису, при котором он ходит во второй; `{id}` это новый родитель, `{tag}` случайная строка) и `expect_when_down` (какие коды ждать, когда второй сервис остановлен) |

## Лаба 5 в GitHub Actions

Проверка лабы 5 подключается в репозитории файлом `.github/workflows/backcheck.yml`:

```yaml
name: backcheck
on:
  pull_request:
  workflow_dispatch:
jobs:
  backcheck:
    uses: bozhedom/backcheck/.github/workflows/lab5.yml@v1
```

На чистой машине GitHub этот workflow копирует `.env.example` в `.env`, выполняет `docker compose up --build --wait` и запускает `backcheck --lab 5 --all --ci`. Зелёная галочка в PR означает, что проект поднимается на чужой машине и проходит автоматические пункты всех пяти лаб.

## Приём лаб

- `backcheck ask --lab N` выдаёт случайный вопрос из банка лабы, с флагом `--edit` ещё и живую правку. В течение дня вопросы не повторяются, `--reset` начинает заново.
- `scripts/deadline-snapshot.sh` записывает, какой коммит был в каждом открытом PR на момент дедлайна. Его удобно запускать по cron в 23:59 накануне встречи.
- Перед каждой встречей чекер прогоняется на эталонном проекте: там всё должно быть зелёным.
